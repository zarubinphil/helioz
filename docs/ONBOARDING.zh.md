# 上手引导

这份引导假设你从来没有跑过智能体传送带。每一步都写清楚要输入什么，以及之后你应该看到什么。如果看到的不一样，就停在那一步：答案在这个差别里，不在页面下面。

你需要 Mac 或 Linux、Node.js 20 以上、git，以及至少一个智能体命令行：`claude`、`codex` 或 `kimi`。除此之外不会在你背后装任何东西。

1. **打开终端，把项目拿下来。** 输入并回车：

   ```bash
   git clone https://github.com/zarubinvibe/helioz.git ~/helioz
   cd ~/helioz
   ```

   你会看到 `~/helioz` 目录出现，终端提示符进入其中。如果 git 说目录已存在，换一个路径，或者先删掉旧的。

2. **运行安装脚本。** 它先自我介绍，然后才动手：

   ```bash
   bash install.sh en
   ```

   你会看到一段简短介绍，然后是对 Node、git 和你的智能体命令行的检查。每个器件都跑自己的自检。最后给你一份清单：什么已就绪，什么还要你自己做。没有这份清单，什么都不会安装。

3. **把想做的事说一次。** 这是传送带唯一需要你说的一句话：

   ```bash
   node scripts/helioz-plan.mjs grill --idea "把计费迁到新表结构"
   ```

   你会看到一个问题，而不是一张表单。每个问题都附带建议答案，所以同意只要一个词。

4. **在你所在的地方回答。** 三扇门通向磁盘上的同一份状态。在编辑器里，把答案写进 `queue/BRIEF.md` 的答案行。在终端里：

   ```bash
   node scripts/helioz-plan.mjs answer --slot goal.done --text "yes"
   ```

   在 Telegram 里，不在电脑前时直接回复机器人。无论走哪扇门，你看到的都是同一份更新后的 brief。

5. **让它写计划。** 关键槽位填好后，两个智能体互不相见各写一份计划，第三个在盲态下合并。

   你会看到 `docs/MASTER-PLAN.md` 里的总计划，以及 `queue/tasks/` 里的小任务，每个都带自己的检查命令。没有检查命令的任务会被拒绝：“做完了”需要证据。

6. **启动传送带。**

   ```bash
   bash scripts/helioz-start.sh
   ```

   你会看到节拍开始：心跳、拉取你的回答、计算预算、选出一个任务，并用真实探针挑出能干活的智能体，而不是相信版本号。

7. **看一个任务被关闭。** 执行者干活，盲检的验证者读磁盘并跑检查命令，完成标记由闸门写下。

   你会看到标记里有前后两个提交、改动文件的哈希和退出码。手写的或从别的任务复制来的标记会被发现，并被当场点名。

8. **读汇报，然后决定停还是继续。** 进展用普通话语发到 Telegram，同时写到磁盘。

   说“停”，传送带冻结且不丢任何东西；说“继续”，它接着跑。三件事永远等你：生产环境的动作、和别人工作的冲突，以及两边都难回头的岔路。

9. **让它熬过夜里。** 上下文用完时，传送带写下交接，看门狗从磁盘拉起新的会话。

   你会看到下一个会话从同一行继续。随时杀掉它：它知道的一切都在磁盘上，不在它脑子里。

10. **验证它没有骗你。**

    ```bash
    node scripts/helioz-probes.mjs
    ```

    你会看到十三个对抗性探针：伪造的标记、旧版本的回执、被改写的日志、被换掉的检查命令、被同时派向同一个文件的两个执行者。它们必须全绿。只要有一个红的，这个项目就没有“就绪”状态。

## 如果这份引导帮到了你

如果 Helioz 在你睡觉的时候推进了工作，请给它点亮星标：[https://github.com/zarubinvibe/helioz](https://github.com/zarubinvibe/helioz)。这只要一秒，却决定别人能不能找到这个项目。

你已经从头到尾跑过一遍，所以你正是能改进它的那个人。路径很短：先 fork 仓库，建一个分支 branch，提交 commit，推送 push，然后开一个 Pull Request。请不要直接向 `main` 推送，发布闸门会拒绝。

有什么坏了，或者某一步写错了？到 [https://github.com/zarubinvibe/helioz/issues](https://github.com/zarubinvibe/helioz/issues) 开一个 issue，写清楚你运行了什么、看到了什么。这份文件里写错的一步，和代码里的缺陷一样，也是缺陷。
